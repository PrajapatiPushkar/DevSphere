# ADR 0006: User Service Introduction & Microservice Data Ownership

* **Status**: Accepted
* **Date**: 2026-08-23
* **Context**: Establishing the domain boundaries and persistence isolation rules for authenticated user profiles versus authentication credentials.

---

## Decision

Introduce **User Service** as an independently deployable microservice owning application user profile data (`first_name`, `last_name`, `display_name`, `bio`, `phone_number`, profile timestamps) and its dedicated MySQL database (`devsphere_user`).

---

## Service Responsibilities & Ownership

- **Auth Service (`devsphere_auth`)**: Owns user credentials (`id`, `email`, BCrypt `password_hash`), user registration, password verification, and JWT generation.
- **User Service (`devsphere_user`)**: Owns application profile data (`user_profiles` table). Uses canonical `userId` generated by Auth Service as the unique identity key.

---

## Architectural Rules

1. **No Shared Database Tables**: Auth Service and User Service MUST NOT share database tables, schemas, or cross-database foreign keys.
2. **Zero Cross-Database Access**: User Service must never directly query `devsphere_auth`, and Auth Service must never directly query `devsphere_user`.
3. **Trusted Gateway Propagation**: User Service relies solely on trusted identity headers (`X-Authenticated-User-Id`) validated and injected by the API Gateway.

---

## Benefits & Rationale

- **Clear Service Boundaries**: Separates core authentication security from domain application state.
- **Independent Database Ownership**: Services can evolve their database schemas independently without risking migration failures in other domains.
- **Reduced System Coupling**: Profile schema changes (e.g. adding bio length, social links) do not impact authentication endpoints or tables.
- **Independent Scaling**: Read/write workloads on profile data can be scaled independently from authentication workloads.
- **Future Event-Driven Extension**: Lay the foundation for future asynchronous user lifecycle events (e.g., user deletion, welcome emails) via messaging systems without tight coupling.

---

## Tradeoffs & Mitigation

- **Distributed Data**: Profile and credential data reside in distinct persistence boundaries.
  - *Mitigation*: The canonical `userId` generated by Auth Service acts as the immutable identity key across services.
- **Distributed User Lifecycle**: Deleting or deactivating accounts requires coordinating across boundaries.
  - *Mitigation*: Account deletion lifecycle is intentionally deferred to future lessons where event-driven patterns can handle multi-service cascade operations safely.
