# DevSphere User Service

## Overview

The **User Service** is the core application domain microservice responsible for managing authenticated user profile information in DevSphere. It operates on port `8082`, consumes centralized configuration from Spring Cloud Config Server (`http://localhost:8888`), and maintains strict database ownership over `devsphere_user` with Redis distributed caching for high-performance profile reads and production-grade Kafka consumer reliability for event-driven profile initialization.

```
Client ──► API Gateway (:8080) ──[JWT Validation]──► User Service (:8082) ──┬──► Redis Cache (:6379) [Cache-Aside]
                                                                              └──► MySQL (devsphere_user)

Kafka Topic (devsphere.user.v1) ──► Consumer (devsphere-user-service) ──[Idempotency & Retries]──► MySQL / DLT
```

---

## Domain Responsibilities

- **User Profile Management**: `first_name`, `last_name`, `display_name`, `bio`, `phone_number`, `created_at`, `updated_at`.
- **Identity Alignment**: Uses canonical `userId` generated by `Auth Service` as profile identity key.
- **Centralized Configuration Import (Lesson 13)**: Fetches non-secret runtime properties from Spring Cloud Config Server (`spring.config.import=configserver:http://localhost:8888`).
- **Service Discovery Registration (Lesson 12)**: Registers as a Eureka client (`DEVSPHERE-USER-SERVICE` on port `8082`) for dynamic service discovery.
- **Distributed Caching (Lesson 9)**: Uses Redis as a distributed cache-aside for `GET /api/v1/users/me` with key format `user-profile:{userId}` and configurable 5-minute TTL. Evicts cache on `PUT /api/v1/users/me`.
- **Production-Grade Kafka Consumer Reliability (Lesson 11)**: Listens to Apache Kafka topic `devsphere.user.v1` (Consumer Group: `devsphere-user-service`) and processes `UserRegisteredEvent` idempotently.
  - **Database-Backed Idempotency**: Uses `processed_events` table (`UNIQUE(event_id)`) to skip duplicate event processing safely.
  - **Atomic Transaction**: Profile creation and `processed_events` insertion execute in the same `@Transactional` boundary.
  - **Offset Acknowledgment**: Kafka offset is acknowledged ONLY after DB transaction commit.
  - **Retries & Backoff**: Configurable delivery attempts (`app.kafka.consumer.max-attempts`, default `3`) and fixed backoff (`app.kafka.consumer.retry-backoff-ms`, default `1000ms`).
  - **Dead Letter Topic (DLT)**: Permanent processing failures, poison messages, and malformed JSON payloads route to `devsphere.user.v1.DLT` preserving original topic, partition, offset, payload, and exception headers.
- **Lazy Profile Fallback**: Fallback profile initialization on `GET /api/v1/users/me` if an authenticated request arrives before Kafka event consumption completes.
- **Zero Authentication Logic**: Does not handle user registration, logins, password verification, or JWT generation/parsing.

---

## Database Ownership & Boundaries

- **Database Name**: `devsphere_user`
- **Tables**:
  - `user_profiles` (`user_id` MUST be unique)
  - `processed_events` (`event_id` MUST be unique)
- **Isolation Principle**: Does not share database tables or foreign keys with `devsphere_auth`. Zero cross-service database access. MySQL is the sole source of truth; Redis holds temporary derived cache data only.

---

## Redis Caching & Resilience

- **Pattern**: Cache-Aside (Lazy Caching).
- **Cache Key Format**: `user-profile:{userId}` (e.g. `user-profile:101`).
- **Cached Object**: `UserProfileResponse` JSON DTO (never JPA entities, credentials, or secrets).
- **Graceful Fallback**: If Redis is down, unreachable, or fails, User Service logs a warning and falls back to querying MySQL cleanly without returning 500 errors or rolling back database updates.

## Security Model & Header Propagation

User Service relies on trusted authentication context propagated by the **API Gateway**:
1. The API Gateway validates the client's Bearer JWT.
2. The Gateway strips any client-supplied `X-Authenticated-User-Id` header.
3. The Gateway injects `X-Authenticated-User-Id: <userId>` into downstream requests.
4. User Service reads `X-Authenticated-User-Id` to identify the user. Requests missing this header return `401 Unauthorized`.

Direct public access to port `8082` in production is disabled. All external requests must pass through API Gateway.
